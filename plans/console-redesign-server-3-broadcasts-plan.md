# Plan — console redesign, server part 3: broadcasts (spec 5)

## Need

The redesigned Broadcasts screens (table with status tabs and 30-day results, detail page
with funnel and opens/clicks over time, one-screen composer that counts recipients) need
three read-side server additions, delivered before their console PR:

1. `broadcasts.list` gains `with_status_counts` and `started_after`;
2. a new route `broadcasts.estimateAudience`;
3. `opened_at` and `clicked_at` time dimensions in the `message_history` analytics schema.

Spec (reviewed): "Spec 5 · Newsletters", "Côté serveur" §1 to §3 and the server
table of "Fichiers, tests et livraison".

Not here: the fix of §4 (template version joined by `broadcasts.get`), a released defect
handled by the separate "published server defects" thread.

No table, column, index, migration or environment variable; `VERSION` stays 44.0.

## Changes

### 1. `broadcasts.list`: `with_status_counts` and `started_after`

- `GetBroadcastsRequest.FromURLParams` reads `with_status_counts` (`true`/`false`, other
  values 400) and `started_after` (RFC 3339; unreadable → 400).
- `ListBroadcastsParams` gains `WithStatusCounts bool` and `StartedAfter *time.Time`. The
  handler builds `ListBroadcastsParams` field by field (`broadcast_handler.go:83-90`): it
  copies both new fields; its test checks it with `gomock.Eq` on the full params.
- `ListBroadcastsTx`: `StartedAfter` adds `started_at >= $n` to the existing conditions, so to
  the count and the rows (a broadcast that never started has `started_at` NULL and is out).
- With `WithStatusCounts`, one more query in the same transaction:
  `SELECT status, COUNT(*) FROM broadcasts WHERE {conditions without the status filter} GROUP BY status`.
  Counts follow the search and `started_after`, not the requested status, so each tab shows
  its own number. A status without broadcast is absent; the console counts it 0.
- `BroadcastListResponse` gains `StatusCounts map[BroadcastStatus]int`
  (`json:"status_counts,omitempty"`), set only when requested.
- The repository interface does not change, only the params type.

### 2. `broadcasts.estimateAudience` (new route)

`POST /api/broadcasts.estimateAudience`, authenticated block of
`BroadcastHandler.RegisterRoutes`; read only, so no `restrictedInDemo`.

```json
{ "workspace_id": "…", "audience": { "list": "…", "segments": ["…"], "exclude_unsubscribed": true } }
```

Response `{ "count": 2214 }`.

- `domain.EstimateAudienceRequest` with `Validate()`: `workspace_id` and `audience.list`
  required; no cap on the number of segments (sending has none).
- `BroadcastService.EstimateAudience(ctx, workspaceID, audience) (int, error)`:
  authentication, then read permission on `broadcasts` and `lists`, and on `segments` when
  the audience has some, modelled on `ListService` (`list_service.go:110-120`). Then
  `contactRepo.CountContactsForBroadcast(ctx, workspaceID, audience)` — the count the send
  uses (`BroadcastOrchestrator.GetTotalRecipientCount`): same list join, same exclusion of
  unsubscribed, bounced, complained and unconfirmed double opt-in, same segment `EXISTS`.
- An unknown list or segment gives 0, not an error.
- `domain.BroadcastService` gains the method; mock regenerated.
- Route classified in `AuditExcludedRoutes` (read), as the audit route test requires.
- `openapi/paths/broadcasts.yaml` (+ schemas, `openapi/openapi.yaml` `$ref`): the new route,
  the new `broadcasts.list` parameters and `status_counts`; `openapi.json` regenerated by
  `make openapi-bundle`.

### 3. `opened_at` and `clicked_at` dimensions

```go
"opened_at":  {Type: "time", Title: "Opened At", SQL: "opened_at", Description: "When the message was first opened or clicked"},
"clicked_at": {Type: "time", Title: "Clicked At", SQL: "clicked_at", Description: "When a link in the message was first clicked"},
```

No index on these columns; the console queries always also filter on `broadcast_id`.

## Plan review and corrections

Review: `reviews/console-redesign-server/plan-3-review.md` in the project files. Every finding
was checked in the code; the corrections below take precedence over the sections above.

- **B1 (decided by Pierre on 12 Nov 2026: stamp on the first sending run, backfill in v44)**:
  `started_at` was only stamped by "send now" and by a resume
  (`broadcast_service.go:433-437, 711-721`), so a scheduled broadcast never got it and
  `started_after` would leave every scheduled broadcast out of the 30-day KPIs.
  - The orchestrator stamps `started_at` on the first sending run (`orchestrator.go`,
    `isFirstSendingRun`) when it is still NULL, never overwriting it. This is a `Fix` line in
    the CHANGELOG (released behaviour: scheduled broadcasts showed no start date).
  - v44 backfills existing rows, approved by Pierre as a data statement: `started_at` set to
    the `created_at` of the broadcast's first message where it is NULL and the broadcast has
    messages; idempotent, never overwrites; appended to `v44WorkspaceStatements()` (part 1),
    so this PR rebases on part 1 and coordinates its v44 step with part 4.
  - Tests: orchestrator unit test (stamped on the first run, kept on later runs and on
    resume); v44 unit test (exact statement, order, error with the workspace ID); integration:
    a scheduled broadcast sent through the real task path gets `started_at` and is kept by
    `started_after`; the backfill sets a scheduled broadcast's start from its first message,
    leaves a set value and a broadcast without messages alone, and runs twice.
- **S1**: the status-count query cannot reuse `ListBroadcastsTx`'s positional placeholders
  minus the status one (`$1 … $4` gap fails on PostgreSQL). The WHERE clause is built by a
  helper that numbers its own placeholders, called once with and once without the status
  filter, keeping today's order so the pinned SQL of `broadcast_postgres_test.go:1269-1284,
  1329-1342` still passes. The status-count query runs **before** the data query (a query on
  the transaction while data rows are open fails with lib/pq). Repo test pins the renumbered
  SQL and args; one integration case combines status, search, `started_after` and
  `with_status_counts`.
- **S2**: `HandleList` writes its own map (`broadcast_handler.go:113-116`): when requested,
  the handler adds `status_counts`, always an object (`{}` when nothing matches); the
  repository returns a non-nil map. A test for each.
- **S3**: `EstimateAudienceRequest` reads `audience` with the same omitted-or-null-means-true
  rule for `exclude_unsubscribed` as `broadcasts.create` (`broadcast.go:507-542`); tested with
  raw JSON bodies (key omitted, null, false, true).
- **S4**: the estimate integration test compares with a real send's recipient count
  (`enqueued_count` / task `total_recipients`, as `TestBroadcastSegmentAudienceSend_Integration`
  does), not with `GetTotalRecipientCount` (same function); the list is double opt-in so the
  pending contact is excluded.
- N1: booleans parsed by `strconv.ParseBool`; invalid case uses `yes`. N2: new
  `GetBroadcastsRequest` fields listed in code; `StartedAfter` converted to UTC. N3: handler
  service error → 500, route in `TestRegisterRoutes`, service authentication failure. N4: only

## As built

Where the code differs from the sections above, or settles what they left open.

- **B1, stamp**: the plan said the repository interface does not change. It gains one method,
  `BroadcastRepository.MarkBroadcastStarted(ctx, workspaceID, broadcastID, startedAt)`:
  `UPDATE broadcasts SET started_at = $3 WHERE id = $1 AND workspace_id = $2 AND started_at IS NULL`.
  A full-row `UpdateBroadcast` would have rewritten status and counters read earlier in the
  run; this statement touches `started_at` only and cannot overwrite a date. The orchestrator
  calls it on every sending run, independently of the event bus, when the broadcast is
  neither paused nor cancelled and its `StartedAt` is nil (code review B2: a scheduled send
  under way during the upgrade, or a failed first write, would otherwise never be dated).
  A full-row write later in the run keeps the stored date (see stale copies below). A failed
  write is logged and the send goes on. The `broadcast.sending_started` event stays on the
  first run, and is not published for a broadcast read as paused or cancelled; when that run
  also writes the date, both carry the same instant. Orchestrator tests that reach a sending run
  of an undated broadcast now allow the call (`AnyTimes`); the new
  `orchestrator_started_at_test.go` pins it: stamped on the first run, with and without an
  event bus, and on a later run without a date; not called when a date is set (first or later
  run), for a paused or a cancelled broadcast, which are not announced either; a write
  failure does not stop the send.
- **Stale copies** (code review B5): `UpdateBroadcastTx` and `UpdateBroadcastStatusTx` write
  `started_at = COALESCE($n, started_at)`, so a cancel or an update holding a copy read before
  the stamp keeps the stored date. Nothing in the code clears a start date. Pinned by
  `TestBroadcastRepository_UpdatesKeepTheStoredStartedAt` (sqlmock) and
  `TestBroadcastStartedAtSurvivesAnOlderCopy` (PostgreSQL, fails without the change).
- **B1, backfill**: a v44 workspace statement, after `statement_timeout` is lifted and before
  the index builds, so it reads `message_history` without their SHARE lock (code review N5):
  `UPDATE broadcasts b SET started_at = m.first_at FROM (SELECT broadcast_id, MIN(created_at) …
  GROUP BY broadcast_id) m WHERE … AND b.status NOT IN ('draft', 'scheduled')`. The grouped
  form is one pass over the table; the correlated `MIN` first written walked the
  `created_at` index once per broadcast, 28 s on a 3-million-message workspace against under
  a second (code review B1). The status condition is an addition to the approved statement:
  `broadcasts.sendToIndividual` records its test send with the broadcast ID, so a draft or
  scheduled broadcast with a test send would otherwise get a start date. A scheduled
  broadcast with messages may also be mid-send: its next sending run dates it. Part 4's
  recount also runs before the index builds.
- **Analytics**: the repository test pins the SQL (`DATE_TRUNC('hour', opened_at AT TIME ZONE
  'Europe/Paris')`, the `inDateRange` bounds as `$2`/`$3`, no `generate_series`), not the bound
  values: the SQL builder hands non-UTC bounds over as UTC instants, not as the strings
  received. The integration test sends UTC bounds and checks the rows.
- **Integration tests**, all against PostgreSQL, with Mailpit for the real sends:
  `TestBroadcastListCounts`, `TestBroadcastEstimateAudience` (compared with a real send's
  `enqueued_count` and task `total_recipients`; 403 without broadcasts, lists, or segments
  read when the audience has segments), `TestAnalyticsMessageEngagement`,
  `TestBroadcastScheduledSendRecordsStartedAt` (fails with the stamp disabled),
  `TestV44BroadcastStartedAtBackfill` (two runs) and `TestBroadcastStartedAtSurvivesAnOlderCopy`.
  The engagement test builds local times with `time.Date` in Europe/Paris, so a clock-change
  day does not shift them, and fails when an hour comes back in two rows.
- **Plan details**: both `mock_broadcast_service.go` and `mock_broadcast_repository.go` are
  regenerated. The estimate tests are in `broadcast_estimate_audience_service_test.go` and
  `broadcast_estimate_audience_handler_test.go`.
- **OpenAPI**: `broadcasts.list` documents `search`, `started_after`, `with_status_counts`,
  the comma-separated `status` with the real status names (the enum listed `sending` and
  `sent`, which do not exist), `status_counts`, the read permission and 403;
  `broadcasts.estimateAudience` is added with its request and response schemas. Lint warnings
  unchanged (all pre-existing).

### Known, not handled

- The backfill dates a sent broadcast from its first message, a test send included: a
  broadcast tested days before it was sent gets the test's date.
- A broadcast paused, cancelled or failed before it ever sent, with a test send, is dated by
  the backfill.
- A scheduled send already under way when the upgrade to v44 runs still has the status
  `scheduled`, so the backfill skips it: it is dated at its next sending run, not at its first
  message. Cancelled before that run, it stays undated.
