# Fix: broadcasts and automation emails are sent one at a time, far below the integration's rate limit

Created 2026-10-21 on `dev` @ `5af5221d`; line numbers are from that commit. Status: **implemented** on `fix/broadcast-send-throughput`. No schema change, so it ships in 42.0 (unreleased).

## What users see

A self-hosted v39 user with one workspace and SES (account quota 100/s) set the integration's marketing rate limit to 3,600/min. Broadcasts plateau around 800/min, while transactional emails pass 1,500/min. The code agrees with them, and dev behaves the same:

| Measured on the real `EmailQueueWorker` (mocked SES and DB latencies) | Rate |
|---|---|
| SES 60 ms + 3 DB writes of 5 ms (their ~75 ms per email) | 780/min |
| No latency at all | 3,005/min, never the configured 3,600 |
| Same queue, a second email integration left at 25/min in the workspace, once sends are concurrent | 1,080/min |

Measured on PostgreSQL 16 with a 200,000-row backlog (a large broadcast queues much faster than it sends): the worker's fetch takes **875 ms per round**, a sequential scan plus an 86 MB on-disk sort, repeated for every batch of 50.

## Verified facts

- **F1 — One email at a time per workspace.** `processWorkspace` sends its batch in a plain loop (`internal/service/queue/worker.go:283-291`). `WorkerCount` (5) only bounds how many *workspaces* run in parallel (`:227`); its comment says "per workspace" (`:16`).
- **F2 — A hard ceiling of 50/s.** `BatchSize` is 50 (`:39`), the poll tick is 1 s (`:202`), and a batch that ends early waits for the next tick. So 3,000/min whatever the latency.
- **F3 — The batch is sized on the slowest email integration of the workspace.** `getMinEmailRateLimit` (`:690`) feeds `(minRate × 45) / 60` (`:255-261`), without the "0 means 60" default the send path applies, so a rate of 0 gives batches of 1. An unused integration left at the console default of 25/min (`console/src/components/settings/Integrations.tsx:2198`) gives batches of 18. The rate limiter then holds such a batch for up to 45 s, and `processAllWorkspaces` waits for every workspace before the next round (`:247`), so one slow integration holds up every workspace on the instance.
- **F4 — The fetch sorts the whole backlog.** `FetchPending` (`internal/repository/email_queue_postgres.go:140-188`) ORs three status branches, which no single index can serve in order. EXPLAIN ANALYZE on 200,600 eligible rows: Seq Scan + external merge sort, **875 ms**. The same eligibility split into three `ORDER BY … LIMIT` branches per integration, joined by `UNION ALL`, uses `idx_email_queue_pending`, `idx_email_queue_retry` and `idx_email_queue_integration`: **4.7 ms** for the integration that owns the backlog, **1.2 ms** for a minority one. A probe for rows of unknown integrations (`integration_id <> ALL(…)`) is a 40 ms sequential scan.
- **F5 — A row is claimed once.** `MarkAsProcessing` is a conditional `UPDATE … WHERE status IN ('pending','failed') OR (processing for over 2 minutes)` that checks the affected row count (`email_queue_postgres.go:190-221`). PostgreSQL re-evaluates the `WHERE` after waiting on the row lock, so two concurrent claims cannot both win. The claim counts the attempt (`attempts = attempts + 1`, `:198`); neither it nor the stuck-processing branch of the fetch (`:161`) checks `attempts < max_attempts`. `FOR UPDATE SKIP LOCKED` in `FetchPending` runs outside a transaction and holds nothing after the statement.
- **F6 — The worker is the only fetcher, and each round is a barrier.** `FetchPending` has no other caller; `processAllWorkspaces` waits for all workspaces (`worker.go:247`) and the loop is sequential (`:196-212`). A row being sent is therefore never re-read by the same process. The one exception is a stop, F16.
- **F7 — Stopping the worker cancels the sends in flight, except over SMTP.** `Stop()` cancels `w.ctx` (`:183`), which the provider call uses (`:426`). A send cancelled after the provider received it returns an error, and `MarkAsFailed` (`:543`) fails on the same cancelled context, so the row stays `processing`, is reclaimed 2 minutes after restart (`email_queue_postgres.go:161`), and is sent again. The token wait comes after the claim (`worker.go:337-357`), so a stop during that wait leaves a claimed row too. SMTP sends take no context at all (`sendRawEmailWithSettings`, `internal/service/smtp_service.go:263`, plain `Dial` at `:267`): cancelling does not interrupt them.
- **F8 — The circuit breaker assumes one send at a time.** `RecordSuccess` closes the circuit unconditionally (`internal/service/queue/circuit_breaker.go:88-95`), so a send still in flight when the circuit opens closes it again. After the cooldown the circuit closes completely (`:70-80`), with no single trial send. A cancelled send (`context canceled`) is unclassified, and the SES classifier counts unknown errors as provider failures (`pkg/emailerror/ses.go`, fallback branch). On dev an opening circuit pauses every broadcast on the integration (`internal/app/app.go:1215-1227`).
- **F9 — SMTP opens one connection per email.** `sendRawEmailWithSettings` dials for each message (`smtp_service.go:267`). A relay that limits concurrent connections answers 421, which counts as a provider failure (`pkg/emailerror/smtp.go:51`).
- **F10 — The rate limiter is safe for concurrent use.** One `golang.org/x/time/rate` limiter per integration, burst 1 (`rate_limiter.go:44`), with `Reserve` available (`:65`). With a burst of 1 it banks no unused time.
- **F11 — Provider services already run concurrently in production.** Transactional emails are sent inside each API request (`internal/service/transactional_service.go:775`). The send path does not mutate the shared integration (`EmailService.SendEmail` copies the request, `internal/service/email_service.go:177-205`). The SDK's shared transport keeps 10 idle connections per host.
- **F12 — A workspace queue can hold rows for several integrations.** An automation email node can override the integration (`internal/service/automation_node_executor.go:221-231`). Rows of a deleted integration go through the "integration not found" path (`worker.go:302-313`) and end as terminal failures after their attempts. That behaviour must be kept.
- **F13 — Pool and shutdown budgets.** `DB_MAX_CONNECTIONS_PER_DB` defaults to 3 (`config/config.go:478`), shared with the API, and `database/sql` waits for a connection without erroring when the context has no deadline. On a signal, `main` gives `Shutdown` 70 s and sets the app's timeout to 65 s (`cmd/api/main.go:63-67`). `Shutdown` cancels the context the worker was started with first (`internal/app/app.go:1772`), then stops the worker (`:1803-1806`) before it shuts the HTTP server down, so whatever the worker's stop takes comes out of the time left for requests.
- **F14 — One existing test checks a copy of the batch formula, not the code.** `TestEmailQueueWorker_DynamicBatchSize` (`worker_test.go:1528-1559`) recomputes the formula inline.
- **F15 — A send in flight escapes a pause when it fails.** Pausing leaves `processing` rows alone (`pauseBySourceSQL`, `email_queue_postgres.go:549-555`), and `MarkAsFailed` writes `failed` with a retry date whatever the row's status (`:248-252`). So a row whose send fails retryably after its broadcast was paused is retried while the broadcast stays paused. The worker calls the breaker's pause before recording the failure that triggered it (`worker.go:442-452`), so today the row that opens the circuit always escapes that pause. With K sends in flight, all those failing for the same reason would.
- **F16 — A stop does not wait for the workspaces in progress.** When `w.ctx` is cancelled, `processAllWorkspaces` returns from inside its loop (`worker.go:231-233`), skipping `processWg.Wait()` (`:247`). The loop then exits and `Stop` returns while workspaces started earlier are still sending. Today their sends are cancelled with `w.ctx` anyway. Once sends survive the stop (Part 3), the app would go on to close the databases under them, and a `MarkAsSent` that fails then means the email is sent again after the restart.

## The fix

### Part 1 — fetch per integration, with an index-friendly query

**`internal/domain/email_queue.go`, `EmailQueueRepository`:**

```go
// FetchPendingForIntegration returns up to limit rows of one integration that are due:
// pending and not out of attempts, failed with a retry date in the past, or stuck in
// processing for over two minutes, oldest first within priority.
FetchPendingForIntegration(ctx context.Context, workspaceID, integrationID string, limit int) ([]*EmailQueueEntry, error)

// FetchPendingOrphans returns up to limit due rows whose integration is not in
// integrationIDs, so that rows of a deleted integration still reach a terminal state.
FetchPendingOrphans(ctx context.Context, workspaceID string, integrationIDs []string, limit int) ([]*EmailQueueEntry, error)
```

`FetchPending` is removed: the worker was its only caller (F6). `SetNextRetry` is removed too (Part 2). Their repository and integration tests go or move to the new methods. The mock is regenerated with the existing `//go:generate` line (`email_queue.go:10`).

**`internal/repository/email_queue_postgres.go`:** `FetchPendingForIntegration` selects `… FROM email_queue q WHERE q.id IN ((pending branch ORDER BY priority, created_at LIMIT $n) UNION ALL (failed branch … LIMIT $n) UNION ALL (stuck-processing branch … LIMIT $n)) ORDER BY q.priority, q.created_at LIMIT $n FOR UPDATE SKIP LOCKED`. Each branch has `integration_id = $i` and exactly today's eligibility rules (`:156-163`), including dev's attempts guard on `pending`. The inner limits pick candidates before the outer `SKIP LOCKED`, so rows locked at that instant by another instance's statement shorten that round (reproduced: with the first 120 pending rows locked, the lane returned only the `failed` ones). Fetches and claims hold locks for one statement (F5), so this costs at most one short round. `FetchPendingOrphans` keeps today's single `WHERE` with `integration_id <> ALL($ids)` added, the ids passed with `pq.Array` as the other repositories do; an empty list matches every row, and `integration_id` is `NOT NULL`. It runs once a minute per workspace (Part 2), so its 40 ms scan is acceptable. No new index: the plans in F4 use existing ones.

### Part 2 — one lane per integration, sized to its rate

**`internal/service/queue/worker.go`:**

- `processWorkspace` runs one lane per email integration of the workspace (`GetIntegrationsByType(email)`), all concurrently, and returns when every lane has finished (the barrier of F6 stays). Non-email integrations get no lane.
- **Lane size:** `laneBatchSize(rate) = clamp(ceil(rate × RoundWindow / 1 min), 1, BatchSize)`, where `RoundWindow = 2 s` and `BatchSize` becomes the per-lane maximum, 200. A rate at or below 0 means 60, as today (`:345-348`). So 3,600/min gives 120 rows, 25/min gives 1, and anything above 6,000/min gives 200. `getMinEmailRateLimit` and the 45-second formula go (F3).
- **Lane concurrency:** `K = SMTPSendConcurrency` for an SMTP integration, otherwise `SendConcurrency` (Part 6; defaults 1 and 10).
- **The circuit decides first.** Before fetching, the lane asks the breaker (`Allow`, Part 5):
  - refused (open within its cooldown, or a probe already out): the lane does nothing this round. Its rows are not fetched, claimed or rewritten, and no token is spent on them;
  - granted as the probe: the lane fetches one row and sends it with that ticket, then ends. If the fetch fails or finds nothing, the row is not dispatched, or its goroutine exits before `SendEmail` for any reason (including a token wait ended by `Stop`), the ticket is cancelled (`CancelProbe`);
  - closed: the lane fetches `laneBatchSize` rows.
- **Dispatch, in fetch order, until a fixed deadline:** the lane sets `deadline = now + RoundWindow` once, right after its fetch returns. Counting from before the fetch would let a fetch slower than the window (a database under load) drop every row, round after round. Letting the first row through whatever its delay, as a review suggested, would bring back the stall of F3 at low rates (one token a minute at 1/min). For each row: take a slot of the lane's semaphore. Stop if `w.ctx` is done or, for a non-probe row, the circuit has opened since (`IsOpen`, read-only). Reserve a token from the integration's limiter. If `now + delay` falls after the deadline, cancel the reservation and stop. Otherwise start a goroutine that waits for the token (a timer against `w.ctx`, cancelling the reservation if the worker stops) and then calls `processEntry`. Rows the lane does not dispatch stay untouched for the next round. Reserving at dispatch keeps the pacing exact. Because the deadline is fixed, the time spent waiting for a slot counts too: a lane held back by its sends rather than by its rate (an SMTP relay at K = 1 with 300 ms per email and a limit of 600/min) stops at the deadline instead of stretching the round for every other lane and workspace. Every round therefore lasts about the fetch, `RoundWindow` and one send, whatever the rate and the latency. That removes the stall of F3 for other workspaces.
- **The breaker's pause waits for the sends in flight.** A `processEntry` whose failure opens the circuit (or re-opens it after a failed probe) hands the classified error to its lane instead of calling `onCircuitOpen`. The lane keeps the first such error and calls `onCircuitOpen` once with it, after all its goroutines have returned. By then every send that was in flight has written its outcome, so `PauseForCircuitBreaker` pauses the rows that failed alongside instead of leaving them `failed` with a retry date (F15). The rows not yet sent are untouched until then, and none is dispatched after the opening.
- **`SetNextRetry` goes.** Its only caller was the open-circuit deferral (`worker.go:318-331`), which the lane-level check replaces: an open circuit now leaves its rows as they are rather than rewriting them one by one.
- **Orphan pass:** at most once per `OrphanCheckInterval` (1 min) per workspace, tracked in a mutex-guarded map, fetch up to 50 rows with `FetchPendingOrphans(emailIntegrationIDs)`. Each one is claimed and failed with "integration not found" through the existing path (`:302-313`), now `failOrphan`. A row of a non-email integration counts as an orphan too: today it would reach the provider with an empty configuration. The pass uses the round's own integration list, so a row being sent by a lane of that round is never an orphan. A pass that comes back with a full batch is due again the next round instead of a minute later, so a deleted integration's backlog drains at 50 rows a round rather than 50 a minute.

### Part 3 — what happens to one row, and with which context

`processEntry` becomes:

1. **Ticket.** The probe row carries the ticket its lane got. Any other row asks `Allow` after its token wait; if refused (the circuit opened meanwhile), it returns and the row stays as it is.
2. If `w.ctx` is done, return without claiming. Otherwise `MarkAsProcessing(w.ctx)`. The token wait now comes before the claim, so no row waits for a token in `processing` (F7).
3. **After a successful claim, two contexts, neither cancelled by the stop:**
   - `w.sendCtx`, derived with `context.WithoutCancel` from the start context and cancelled only when the shutdown grace runs out (Part 4), for what leads up to the email leaving: the stop-on-reply guard, the pre-send history upsert and `SendEmail`. Aborted there, the email has not been accepted, or its fate is unknown, as today on a stop;
   - `w.writeCtx`, `context.WithoutCancel` of the start context and never cancelled, for what records the outcome: `MarkAsSent`, the history upsert, `handleError` with its history upsert, `MarkAsFailed` and `MarkAsPermanentlyFailed`, and the callbacks. An SMTP send ignores the abort (F7), and an HTTP send can return just as it fires; when such a send succeeds during `AbortWait`, the databases are still open and `MarkAsSent` must not fail on a cancelled context, or the email is sent again after the restart.

   Neither gets a deadline: a `MarkAsSent` cut short by one would resend the email.
4. **A probe that is not sent is given back.** Every return before `SendEmail` (stop, claim lost, the stop-on-reply guard removing the row) cancels a probe ticket with `CancelProbe`, so the next round can probe at once instead of after another cooldown.
5. The result is recorded with the ticket: `RecordSuccess(id, ticket)` or `RecordFailure(id, ticket, err)`. A failure that reports `opened` goes to the lane (Part 2). The progress callbacks (`SetCallbacks`, which only tests use) are now called from concurrent sends, and their comment says so.
6. If `SendEmail` fails and `w.sendCtx` is done, the send was aborted by the shutdown grace, not refused by the provider. Log at warn and return: no breaker record (a probe ticket is cancelled), no `MarkAsFailed`. The row stays `processing`, keeps the attempt its claim counted, and is retried 2 minutes after restart: today's outcome for the email in flight on a stop (F7). A send that succeeds after the abort is recorded normally, through `w.writeCtx`.

### Part 4 — stopping without cutting sends

- `Start` creates `w.sendCtx, w.abortSends = context.WithCancel(context.WithoutCancel(ctx))` and `w.writeCtx = context.WithoutCancel(ctx)`.
- `processLoop` skips the retention sweep once `w.ctx` is done; today it runs it on a cancelled context after the last round and logs a spurious error when the hourly sweep is due (`worker.go:209-211`, `:649`).
- **`processAllWorkspaces` always waits for the workspaces it started** (F16): on a cancelled `w.ctx` it stops starting new ones (`break` out of the loop, not `return`) and still reaches `processWg.Wait()`. Each `processWorkspace` waits for its lanes, and each lane for its goroutines, so the loop exits only once every send it started has finished.
- `Stop` sets `running = false`, cancels `w.ctx` so no new token or claim is taken and pending token waits end, then waits for the loop up to `ShutdownGrace` (10 s). On timeout it logs, calls `w.abortSends()`, waits at most `AbortWait` (5 s) more, and returns, logging the sends still running. SES and the HTTP providers return when cancelled, and their rows stay `processing` to be retried after the restart, as today. An SMTP send cannot be cancelled (F7): if it ends before the databases close, its outcome is recorded through `w.writeCtx`; otherwise its row stays `processing` too. At worst 15 s comes out of the requests' share of the shutdown (F13); a normal stop takes the length of the sends in flight.
- In-flight sends normally take well under a second, so a stop during a broadcast loses or repeats nothing. Rows that never got a token stay `pending`.

### Part 5 — a circuit breaker that tolerates concurrent sends

**`internal/service/queue/circuit_breaker.go`**, all under the existing mutex. Each breaker gains `epoch` (incremented each time the circuit opens), `openedAt` and `probeInFlight`. The worker gets a `Ticket{Epoch uint64; Probe bool}` per send. Epochs replace timestamps: a send's ticket says which opening it predates, however late the send actually starts.

- **`Allow(integrationID) (Ticket, bool)`** replaces the mutating `IsOpen` in the worker:
  - closed: `{epoch, false}`, granted;
  - open, the cooldown elapsed since `openedAt` and no probe out: sets `probeInFlight` and grants `{epoch, true}`;
  - otherwise refused.
- **`CancelProbe(integrationID, ticket)`:** for the current epoch's probe on an open circuit, clears `probeInFlight`. Anything else does nothing.
- **Closing** (a probe's success or recipient error) clears `isOpen`, `probeInFlight`, the failure count and the last error together, so the next opening starts with no probe out.
- **`RecordSuccess(integrationID, ticket)`:** on an open circuit, closes it only for the current epoch's probe. On a closed circuit, resets the failure count only for a ticket of the current epoch. A success from an earlier epoch moves nothing: that send was allowed before the circuit opened.
- **`RecordFailure(integrationID, ticket, err) (counted, opened)`:**
  - a recipient error is never counted. If it is the current epoch's probe, it closes the circuit: the provider answered. Today the manager returns before reaching the breaker on a recipient error (`circuit_breaker.go:189`); it now passes the probe case through;
  - a provider or unknown error with a current-epoch ticket on a closed circuit counts. The failure that reaches the threshold opens the circuit (`epoch++`, `openedAt = now`) and reports `opened` once, under the mutex, however many fail together;
  - a failed probe re-opens the circuit (`epoch++`, `openedAt = now`, probe cleared) and reports `opened`, which keeps today's "fires again after each cooldown" for the idempotent pause;
  - anything else comes from a send allowed before the latest opening and is ignored.
- **Cooldown** runs from `openedAt`, so late failures no longer extend it.
- **`IsOpen`** becomes a read-only accessor, and `GetStats` computes `CooldownLeft` from `openedAt` and reports a probe in flight.
- A probe that never returns keeps the circuit open; such a send also stalls the worker ("Not in scope").

## Not in scope

- **A send that succeeds and then `MarkAsSent` fails** (database unavailable): the row is resent 2 minutes later, and since the code returns before the history upsert (`worker.go:460-470`), the first send leaves no trace. This predates the fix, and its probability per email is unchanged. Closing it means writing the history before deleting the row and checking it before re-sending a reclaimed row. Separate PR.
- **The SDK's own retries** after a connection reset or a network timeout can repeat a send SES had accepted. This predates the fix too.
- **A provider call that never returns** stalls the worker for every workspace, as today, and a probe that never returns keeps its circuit open. A per-send timeout would turn the stall into a possible duplicate, so it needs its own rule for ambiguous sends. Only the shutdown grace aborts such a call, and not over SMTP.
- **Several instances on one database:** each has its own rate limiter, so the limit applies per instance. A send that outlives the 2-minute reclaim can be sent again by another instance, a reclaimed row on its last attempt gets one more try, and `MarkAsFailed` has no status guard (F5). All unchanged; on one instance the round barrier keeps a row in flight from being fetched again. Guarding the claim with `attempts < max_attempts`, as a review suggested, would leave a crashed last attempt in `processing` forever. The claim now checks the fetch's conditions on pending and failed rows only (see the amendments), which leaves that branch alone.
- **Outcome writes that do not know their claim.** The claim checks that a row is due, not that it is the version this instance fetched, and the writes that record a send's outcome (`MarkAsFailed`, `MarkAsPermanentlyFailed`, `MarkAsSent`) check nothing at all. With several instances, a row another instance claimed and that became due again within the round (a broadcast paused and resumed in those two seconds, or a retry delay set below the round) is claimed with the attempt count fetched before, which `handleError` then trusts. On dev the window was a whole batch, up to about 45 s. And a send slow enough to look stuck is claimed again by another instance; the first send's failure, written later, then lands on a row it no longer owns: it can leave a row `failed` with a retry date and no attempt left, which no fetch takes and which stays counted as still being sent (the broadcast can then never be retried), revive a row the other instance gave up on, or take a paused row out of its pause. All of this predates the fix and needs several instances. Guards on `MarkAsFailed` alone were tried after the reviews and dropped: one gave up a row another instance was still sending, which let a broadcast retry requeue it under that send; the next left the caller's own stale claim stranded. This needs its own plan, which also gives up the rows earlier releases left stranded (failed, pending or paused with no attempt left become failed with no retry date and a processed date, so they stop counting as being sent, the retention sweep collects them and a broadcast retry can requeue them; resetting them would mail recipients already reported as failed). The reviews of this plan left these constraints for it:
  - A claim is identified by the `updated_at` that `MarkAsProcessing` stamps, returned with the attempt count: the count alone comes back after a broadcast retry resets it to 0. `handleError` takes its attempt count from the claim, not from the fetch.
  - The delete after a successful send stays unconditional: an email that went out removes its row whoever holds it, or a later claim's failure schedules a second copy. The stop-on-reply cancel, which deletes through the same `MarkAsSent` without sending, needs a delete tied to the claim.
  - A claim found stale before the send skips the send, not only its history write.
  - History: a failure must not mark as failed an email another claim delivered, a stale claim's pre-send upsert must not erase the current claim's failure, and a stale success and a current failure must land in a known order. Writing the queue row and its history together would order them, but a failed history write (a broken `contact_timeline` trigger) must not undo the delete after a successful send, or the email goes out again every 2 minutes.
  - The order of writes must agree with "A send that succeeds and then `MarkAsSent` fails" above, which changes the same writes, and its history check needs a mark of a completed send that the pre-send upsert cannot leave (that upsert looks like a success, so a send cut by a crash or by the shutdown would be skipped).
- **A manual pause while a send fails** (F15): a send in flight when the user pauses, that then fails retryably, is retried while the broadcast stays paused. With K sends in flight, up to K rows per integration instead of one, and only when sends fail during the pause. Closing it means pausing `processing` rows and guarding `MarkAsFailed`, which changes what pause, resume and cancel do to rows in flight, the code the duplicate-sends fix is changing. Separate PR, after that one.
- **Throttling still counts as a provider failure.** Slowing the limiter down on a throttle, instead of opening the circuit, would be a separate change. The docs and console text cover the configuration side.
- **A per-integration concurrency setting in the console.** The environment variables are enough for now.
- **A composite index `(integration_id, priority, created_at) WHERE status = 'pending'`.** It is not needed per F4, and could be revisited if a minority lane ever carries a huge backlog.
- **A continuous pipeline without the per-round barrier.** It would win about 4 % (3,475 vs 3,600/min measured) but needs claiming inside the fetch.

## Effects to state in the release

- The configured rate becomes the real rate, to about 96 % in sustained sending: each 2 s round spends some 80 ms fetching and settling, and the limiter banks no unused time (F10). Measured 3,475 of 3,600/min.
- A limit above what the provider accepts, net of transactional traffic, now leads to throttling. Throttling opens the circuit, and on 42.0 the circuit pauses the integration's broadcasts. After the cooldown, the integration sends one test email and resumes at full rate if it goes through.
- One lane tops out at about 6,000/min (200 rows per 2 s round). Above that, raise `BatchSize`, which is not exposed. That is acceptable for 42.0 and is stated in the docs.
- A lane also tops out at K divided by the time one email takes: with SMTP at K = 1 and 300 ms per email, about 200/min whatever the limit, as today. The docs say to raise `EMAIL_QUEUE_SMTP_CONCURRENCY` when the relay accepts several connections.
- Rounds still cover at most `WorkerCount` (5) workspaces at a time. When more than five workspaces have emails queued at once, they take turns, as today, and each sends below its limit. The reporter's case (one workspace) is not affected.
- Each send makes about three queries on the workspace's pool, 3 connections by default and shared with the API. With a remote database, `DB_MAX_CONNECTIONS_PER_DB` may need raising to reach high rates.

## Amendments after the code review

The implementation's first full review (`e2bc9597`) found the following; each change came with a test that failed before it.

- **A send refused after the opening is held, whatever the provider calls it.** With K sends in flight, those allowed before the circuit opened and refused after it share the outage that opened it. A refusal the provider calls permanent (SES `AccessDenied`, an unverified sender) was given up at once, so the pause could not hold it: up to threshold + K − 1 recipients given up per opening, where one at a time gave up the threshold. `processEntry` now schedules such a failure for a retry when it is a provider error the breaker did not count and the circuit is open, so the pause holds it. The failures that opened the circuit are handled as before, a probe's failure too, and a row on its last attempt is still given up. Test: worker_test `a send in flight that fails after the opening is kept for a retry, even when the provider calls it permanent`.
- **No fetch without a token.** A lane first checks that its integration's next token falls within the round (`IntegrationRateLimiter.TokenDueBy`, which takes nothing), before asking the breaker, so no probe is taken for a round that cannot send it. At 10/min, five rounds out of six fetched and sent nothing. Tests: worker_test `a lane whose next token falls after the round does not fetch`, `TestIntegrationRateLimiter_TokenDueBy`.
- **The orphan fetch takes the lane's shape.** `FetchPendingOrphans` uses the same three branches as `FetchPendingForIntegration`, built by one function (`dueRowsSQL`), with `integration_id <> ALL($1)`. With 200,000 rows of a deleted integration, the single `WHERE` sorted all of them on disk (350–390 ms); the branches read their indexes (2–5 ms). Without orphans the pass costs what it did (50–100 ms), once a minute. A pass that comes back full is due again the next round. Test: the repository test pins the branches.
- **Both fetches recheck eligibility under the lock**, as Part 1 requires ("exactly today's eligibility rules"). With the conditions only inside `id IN (…)`, a row another instance changed after the statement began was locked in its new version and returned without a recheck, since PostgreSQL rechecks only the outer conditions: a row another instance had just failed, with a retry date or for good, could be claimed and sent again at once. The outer `WHERE` now repeats the filter and the three conditions (no measurable cost: the outer query is driven by the id list), and each branch parenthesises filter and condition. Found by the second review, on the changes only. Test: the repository tests pin the outer conditions.
- **Start after an unfinished Stop.** Stop can return before the loop does, when a send ignores its cancellation. `Start` now refuses while the previous loop runs, instead of replacing the contexts that loop reads and running a second loop beside it, and `Stop` waits on a channel closed when the loop returns rather than a WaitGroup `Start` would reuse. Test: worker_test `Start refuses to run beside a previous run still finishing a send`.
- **The claim checks that the row is still due.** `MarkAsProcessing` took any `pending` or `failed` row. With several instances, another one can fail a row between this instance's fetch and its claim (up to a round): the row was then claimed and sent again at once, before its retry date or after it was given up. The claim now uses the fetch's three conditions, so the stuck-processing branch is unchanged and a send cut by a crash on its last attempt is still recovered (the objection under "Not in scope" was to an attempts guard on that branch). On one instance the round barrier already prevented it. Found by the third review, on the changes only. Test: integration `TestEmailQueueFetchEligibility`, `a row is claimed only while it is due` (each not-due row refused with its attempts unchanged; due rows and a last-attempt stuck row claimed), which failed before; the unit test pins the conditions.
- **Late failures over another instance's claim: kept out, after two tries.** The fourth review found that a failure written late, after another instance claimed the row again and spent its last attempt, left the row `failed` with a retry date nobody takes. Two guards on `MarkAsFailed` were tried in turn, and the reviews of each found a worse case (a row given up while another instance was still sending it, then the caller's own stale claim stranded). Without knowing which claim a write belongs to, no condition on the row gets every case right, so `MarkAsFailed` is unchanged from dev and the case moves to "Outcome writes that do not know their claim" under Not in scope, which also gives up the rows earlier releases already stranded.
- **One list of due conditions.** The fetch branches, the recheck under the lock and the claim are all built from `emailQueueDueKinds`, so a condition added later cannot reach one of them and miss the others.
- **`IntegrationRateLimiter.Wait`, `Reserve` and `Allow` are removed**: nothing calls them, and they paced without the round's deadline. `Stop` reads the abort function under the lock, since a `Start` can replace it once the loop is done.
- **Kept out of scope, measured:** a lane whose rows are queued behind another integration's large backlog in the same workspace walks that backlog through `idx_email_queue_pending`: 100–180 ms per round behind 200,000 rows, where dev took 600–740 ms for the same queue. A partial index `(integration_id, priority, created_at) WHERE status = 'pending'` brings it to 3–5 ms (built in 0.4 s on 400,000 rows), but it is a schema change, for a separate PR if wanted. The CHANGELOG no longer says the fetch stays fast in every case.

## Changelog (`## [42.0] - WIP`)

- **Improvement**: Broadcasts and automation emails now go out at the rate limit set on their email integration. Each email integration sends up to 10 emails at once (1 over SMTP), where a workspace sent one at a time and never more than 3,000 per minute, and the queue is fetched without sorting its whole backlog each time. Keep the limit at or below what your provider accepts, minus your transactional traffic. `EMAIL_QUEUE_CONCURRENCY` and `EMAIL_QUEUE_SMTP_CONCURRENCY` set the number of simultaneous sends.
- **Improvement**: Restarting Notifuse during a broadcast now lets the emails being sent finish instead of sending them again after the restart. When a provider failure pauses broadcasts, the emails being sent at that moment are paused with the rest, and the integration's other queued emails, such as automation emails, go out again after the cooldown, starting with a single test email. An integration with a low rate limit no longer holds up the sends of other workspaces.
- **Improvement**: With several Notifuse instances on the same database, an email that one instance has just failed or given up on is no longer sent again straight away by another.
