## Problem

Verified on `dev`:

1. `workspaceRepository.Create` creates the database before inserting the row (`internal/repository/workspace_postgres.go:104`); if the insert fails it drops the database (`:121-124`), but not if the creation itself fails.
2. `EnsureWorkspaceDatabaseExists` (`internal/database/utils.go:133`) runs `CREATE DATABASE`, then `InitializeWorkspaceDatabase` (`internal/database/init.go:88`), which runs every statement with its own `db.Exec`, no transaction. A failure partway (restart, timeout, PostgreSQL restart, a statement the server rejects) leaves a half-built database and returns an error, so no row is saved.
3. When the database already exists, `EnsureWorkspaceDatabaseExists` does nothing: no creation, no initialisation (`utils.go:161`).
4. The console derives the ID from the name deterministically (`console/src/pages/CreateWorkspacePage.tsx:23-30`), so retrying the form sends the same ID. The retry passes the row check, finds the database, skips initialisation, inserts the row: a registered workspace with a partial (or empty) schema. Every request touching a missing table fails.
5. A failing workspace migration aborts startup for the whole instance (`internal/migrations/manager.go:269-276`, reaching `logger.Fatal` through `internal/app/app.go:368`). The first future workspace migration (v43+) that touches a missing table stops the instance from starting.
6. A registered workspace whose database is missing (`Delete` drops the database before deleting the rows, `workspace_postgres.go:351`; a failed row deletion leaves exactly that) makes `defaultConnector.connectToWorkspace` fail with "database does not exist" (`manager.go:38-56`), which also aborts startup when a workspace migration is pending, with no explanation.
7. Two concurrent creates of the same ID both pass the service's and the repository's row checks (`internal/service/workspace_service.go:292`, `workspace_postgres.go:81`). If they overlap at `CREATE DATABASE`, the second fails with 42P04 (or 23505 on `pg_database_datname_index`, seen on the test server) and nothing is dropped; if the second arrives after the first created the database, it skips creation (`utils.go:161`), loses the row insert on the primary key (`workspaces.id`, `internal/database/schema/system_tables.go:26`) and drops the database (`:121-124`) the winner just registered.
8. Between `Delete`'s drop and its row deletion (`workspace_postgres.go:351`, `DeleteDatabase` at `:445-475` closes the pool then drops), a request or background worker for that workspace passes the registration check (the row is still there), hits 3D000 and has the connection manager recreate and initialise the database (working tree `connection_manager.go:395`). The rows then go and the database stays, with tables. Today the next create of that ID adopts it silently (problem 3). With part A's W3 alone, that create would get a 409 for good, and the demo reset (`internal/service/demo_service.go:181-207`, then `"demo"` again at `:286`) would fail on every later reset. The email queue worker lists every workspace each second (`internal/service/queue/worker.go:70`, `:385`).

- lib/pq v1.10.9 `watchCancel` (`conn_go18.go:102-140`): when the context ends while a statement runs, the watcher marks the connection bad, sends a cancel request, and the statement's finish function closes the connection, **even if the statement itself succeeded**; `ExecContext` then returns nil (`conn_go18.go:36-47`).

Checked on the test server (`postgres:17`, `tests/compose.test.yaml`) with throwaway Go programs (lib/pq v1.10.9):

- An advisory lock carries the current database's OID in `pg_locks.database`, so it only contends with sessions in the same database.
- A **session** advisory lock on a pinned `sql.Conn` survives `Conn.Close()`: the connection goes back to the pool still holding it (only `DB.Close()` released it). Behind a transaction-mode pooler, a session lock and its unlock can also land on different server connections. Hence a **transaction-level** lock below.
- A **transaction-level** lock (`pg_advisory_xact_lock`) held by an open transaction on the admin database: `CREATE DATABASE` and `DROP DATABASE ... WITH (FORCE)` succeed on other connections meanwhile; the idle-in-transaction holder has `backend_xmin` NULL (it pins no snapshot, so it does not hold back vacuum); a waiter is cancelled by its context after its deadline; the lock is released on rollback, with no lock left on the pooled connection.
- **But** database/sql rolls back a `BeginTx(ctx)` transaction the moment `ctx` ends: cancelling the holder's context while its work is still running released the lock (another session got it 8 ms later), and the later `Commit` returned "transaction has already been committed or rolled back". A lock transaction begun on `context.WithoutCancel(ctx)`, with the lock statement itself run under the caller's `ctx`, stayed held after the cancellation and was released on commit.
- **And** a waiter whose context ends just as the lock is granted can get nil from `pg_advisory_xact_lock` with its connection closed by lib/pq and the lock gone: 300 runs ending the waiter's context right after the holder committed gave 0 errors, about 180 locks really held, about 120 returned nil with **nobody** holding the lock (`pg_locks` from another session; reproduced twice).
- With `transaction_timeout = 1s` as the session default, `SET LOCAL idle_in_transaction_session_timeout = 0` does not save the holder: PostgreSQL 17 terminates the connection ("terminating connection due to transaction timeout") and the lock goes; `SET LOCAL transaction_timeout = 0` keeps it. A role-level `lock_timeout` or `statement_timeout` aborts a lock wait (55P03, 57014). All four settings have `pg_settings.context = user`. `transaction_timeout` exists only from PostgreSQL 17; the README requires 17, the docs only recommend it.
- The two-key form is `pg_advisory_xact_lock(int4, int4)`: a class key above 2^31-1 fails (`function pg_advisory_xact_lock(bigint, integer) does not exist` as a literal, out of range as a parameter).
- `CREATE OR REPLACE FUNCTION track_contact_changes() RETURNS TRIGGER` fails with "cannot change return type of existing function" when a function of that name returning `int` exists. That statement is in the trigger phase (`init.go:578`), after every table, so planting that function gives a deterministic late failure. (A planted composite type does not work: `CREATE TABLE IF NOT EXISTS` treats it as an existing relation and skips.)
- `CREATE EXTENSION pg_stat_statements` creates two views in `public`, both found as extension-owned through `pg_depend`. Another session's temporary table does not make a database look non-empty with the W1 query.
- v42's workspace step fails on an empty database (`UPDATE segments`), and is a no-op on a fresh schema.

## The name lock

A transaction-level advisory lock held by an open transaction on its own connection while the work runs on other connections. The helper that builds the lock transaction is shared with part B's migration lock:

- **It outlives the caller's cancellation**: the lock transaction is begun on `context.WithoutCancel(ctx)` bounded by its own hold timeout (10 minutes, as `deleteWorkspaceTimeout`), and only the lock statement runs under the caller's `ctx`, so a cancelled caller stops waiting but never releases a lock whose work is still running.
- **A lock granted as the caller's context ends is not trusted**: after the lock statement returns nil, `ctx.Err()` is checked; if it is set, the lock is treated as not taken (rollback, the context error returned, `fn` not called). lib/pq closes the connection in exactly that case, releasing the lock; once the statement has returned, its watcher has settled, so a nil `ctx.Err()` at that point means the connection was kept.
- **The work ends before the lock can**: database/sql rolls the lock transaction back when the hold timeout fires, so `fn` gets a context bounded one minute short of it (and by the caller's own deadline), and every statement under the lock runs on that context: `CREATE DATABASE`, the connection, the initialisation (through an unexported `initializeWorkspaceDatabase(ctx, db)`; the exported `InitializeWorkspaceDatabase(db)` calls it with `context.Background()`), the emptiness check, the row checks, the insert and the row deletion.
- **A cleanup drop gets its own bound**: a drop after a failure runs on `context.WithoutCancel` bounded by `min(now + dropDatabaseTimeout, hold deadline − 30 seconds)`, independent of the caller's deadline: the failure may be that deadline passing (the connection manager's `createCtx` only expires), and a drop under it would be refused before it is sent.
- Once the work has succeeded, a commit or rollback error of the lock transaction is logged, not returned: the work is done, and the server releases the lock with the transaction or the connection anyway.
- **A dead holder is noticed within about a minute**: right after `BEGIN`, `SET LOCAL tcp_keepalives_idle = 30`, `tcp_keepalives_interval = 10`, `tcp_keepalives_count = 3` (all `pg_settings.context = user`, checked on the test server; ignored on a Unix-socket connection). The client-side hold timeout dies with its node, so without them a holder whose node disappears keeps the lock until the server notices the dead connection, about 2 hours with Linux defaults: for the name lock, that blocks the workspace's creation, deletion and 3D000 fallback, and a startup waiting on it in W4 (`RunMigrations` runs on `context.Background()`). Their effect is checked by a probe during implementation, not in CI: the holder runs in its own container on the test network, the container is disconnected (`docker network disconnect`, so the server's probes go unanswered), and another session must get the lock within about a minute. If the probe shows no effect, Pierre is told before going further.
- **No server setting can end it early or abort its wait**: right after `BEGIN`, `SET LOCAL statement_timeout = 0`, `lock_timeout = 0`, `idle_in_transaction_session_timeout = 0`, and `transaction_timeout = 0` when the server has it (`set_config('transaction_timeout', '0', true)` only if `current_setting('transaction_timeout', true)` is not NULL, so PostgreSQL 16 and older still work). Bounds come from the contexts.
- **Its own connections**: the admin `*sql.DB` is opened per call with at least 2 connections (lock + work) and `connect_timeout=10` on its DSN (a new admin-DSN builder for these paths; `GetPostgresDSN` itself unchanged).
- **Key**: `pg_advisory_xact_lock(<workspace class key>, hashtext(<database name>))` in a transaction on the `postgres` admin database, which every caller can reach. The class key is a new `int32` constant (the two-key form takes `int4`; a constant styled like `secretKeyRotationLockID` would fail at runtime, and sqlmock would not notice); it cannot collide with `secretKeyRotationLockID`, which uses the single-bigint form on another database. Serialises, per database name and across instances, everything that checks, creates, initialises or drops a workspace database in parts A and B, together with the workspace-row checks that decide it. A hash collision only serialises two unrelated names; hashing happens on the one server, so the hash function's stability across versions does not matter.
- **No nesting**: code running under the lock never calls a function that takes it (an unlocked internal variant is used instead); taking it again from another connection of the same process would wait on itself until its context ends.
- **42.2 and older instances do not take it**: during a rolling deploy, the old pods still create and delete workspaces as today until they are gone. Said in the PR.

## Changes

### W1. Initialisation in one transaction, and an emptiness check (`internal/database/init.go`)

- `InitializeWorkspaceDatabase(db *sql.DB) error` keeps its signature but runs every statement inside one transaction (`BeginTx`, `tx.Exec`, `Commit`, rollback on any error), through `initializeWorkspaceDatabase(ctx, db)`. A failure leaves no partial schema. Its statement list moves to an unexported `runWorkspaceSchema(ctx, tx)`. The transaction starts with `SET LOCAL statement_timeout = 0` and, when the server has it, `transaction_timeout = 0` (as v42 does): a role-level `transaction_timeout` would otherwise apply to the whole initialisation instead of each statement; the bound is the context.
- New `WorkspaceDatabaseHoldsTables(ctx context.Context, db *sql.DB) (bool, error)`: true when the database has a relation of kind `r`, `p`, `v`, `m`, `S` or `f` in a schema other than `information_schema` and those matching `pg\_%` (covers `pg_catalog`, `pg_toast*` and other sessions' `pg_temp_*`, which are visible in `pg_class`; user schemas cannot start with `pg_`), not owned by an extension: `NOT EXISTS (SELECT 1 FROM pg_depend d WHERE d.classid = 'pg_class'::regclass AND d.objid = c.oid AND d.deptype = 'e')`.

### W2. Name lock, and drop what this call created (`internal/database/workspace_lock.go` new, `internal/database/utils.go`, `pkg/database/connection_manager.go`)

- A shared helper `WithLockTransaction(ctx, db, lockSQL, args, fn)` (exported because part B's migration manager uses it on the system database) builds the lock transaction on any `*sql.DB`.
- New `WithWorkspaceDatabaseLock(ctx, cfg, dbName, fn func(ctx context.Context, admin *sql.DB) error) error`: opens the admin database, begins the lock transaction as described above, takes the name lock, checks `ctx.Err()`, runs `fn` (which uses other connections of `admin`), then commits; rolls back on any error or panic. Exported because `Delete` (W5), the migration manager (W4), part B and the integration tests' barrier use it.
- `EnsureWorkspaceDatabaseExists(ctx, cfg, workspaceID, stillRegistered func(ctx) error)` gains a context and a registration check (the connection manager passes `createCtx` and its registration check; `nil` for `ConnectToWorkspace` and the test helpers). It reaches the function through a new field, `ensureWorkspaceDatabase`, same pattern as the working tree's `openPool` seam, so its test can observe both. Inside the name lock, first `stillRegistered` (its error stops everything before any query on the database: a request arriving during a `Delete` waits on the lock, then finds the workspace gone and creates nothing), then:
  - database missing → `CREATE DATABASE`, connect, initialise **without** the emptiness check (a database copied from a `template1` that holds a user table must still get its schema; re-running over a complete schema is harmless). If the connection, ping or initialisation fails: close the workspace connection, `DROP DATABASE IF EXISTS <quoted> WITH (FORCE)` on the cleanup bound above, return the setup error; if the drop also fails, the error says both, and the database is left empty (W1). On the connection manager's path such a leftover is a registered workspace with an empty database, which part A does not repair (part B does) (it no longer reaches 3D000): the separately bounded drop is what keeps that rare;
  - database exists and holds no tables → initialise it (only callers for registered workspaces reach this, so repairing is right); a caller that waited while another initialised finds tables and does nothing;
  - database exists and holds tables → nothing, as today.
- It never drops a database it did not create in the same call. No pre-PostgreSQL-13 fallback for this drop.

### W3. Workspace creation under the name lock (`internal/database/utils.go`, `internal/repository/workspace_postgres.go`, `internal/domain`, `internal/service/workspace_service.go`, `internal/http/workspace_handler.go`)

- New `CreateWorkspaceDatabase(ctx, cfg, workspaceID, registered func(ctx) (bool, error), insert func(ctx) error) error`: the whole creation runs inside the name lock, in this order:
  1. `registered` → the row exists → `domain.ErrWorkspaceAlreadyExists`, nothing touched (a registered workspace's database is never initialised by a create);
  2. database missing → create and initialise as W2;
  3. database exists and holds no tables → initialise it (an orphan left by a failed creation, or by the test pool helper);
  4. database exists and holds tables → `*domain.ErrWorkspaceDatabaseNotEmpty{WorkspaceID, DatabaseName}`, nothing changed;
  5. after 2 or 3, `insert`; if it fails → `registered` is asked again (an insert can commit and still report an error, on a connection reset): registered → nil, nothing dropped; not registered → the database is dropped with the unlocked drop on the cleanup bound (created or adopted, it holds nothing yet), and the insert error returned; the re-check itself failing → nothing dropped, the insert error returned.
- Two concurrent creates of the same ID now serialise: the second one waits, then finds the row and gets "workspace already exists" (problem 7), never the "remove that database" message.
- **Detached from the client**: `CreateWorkspace` detaches from the request before `repo.Create` (`context.WithoutCancel` + a 5-minute `createWorkspaceTimeout`) and keeps that context for the membership, contact, list and tasks that follow, so a client disconnecting mid-way cannot leave a workspace without its owner. `repo.Create` detaches the same way on its own, for its other caller (the demo reset).
- `workspaceRepository.Create` keeps its pre-lock row check as a fast path, now returning `domain.ErrWorkspaceAlreadyExists` too (today's `workspace with ID %s already exists` becomes a 500 when a create slips between the service's check and this one), then calls `CreateWorkspaceDatabase` through a repository field (`createWorkspaceDatabase`, defaulting to the database package function: the seam the repository test needs), passing its row check as `registered` and the insert as `insert`. The existing `ForgetUnknownWorkspace` call stays after a successful insert.
- `CreateDatabase` leaves `domain.WorkspaceRepository` and the repository (mock regenerated with `go generate`): nothing calls it any more, and left in place it would create databases for IDs nobody registered. Its tests move to the new function; the hand-written test methods listed above go, and the connection manager's comment points at `CreateWorkspaceDatabase`.
- `domain.ErrWorkspaceAlreadyExists` (message "workspace already exists") replaces the service's `fmt.Errorf("workspace already exists")` (`workspace_service.go:292-294`); the handler maps it with `errors.Is` to 409 "Workspace already exists", keeping today's response.
- `domain.ErrWorkspaceDatabaseNotEmpty.Error()`: `a database for workspace ID "<id>" already exists and holds tables, but no workspace uses it (<database name>): choose another ID, or remove that database`. The handler maps it to **409** with that message. Accurate because the row check happens inside the lock. The console needs no change.
- Why such a database is refused rather than adopted: with W1, a leftover database holds either no table or a complete schema of the version that built it; an unregistered database receives no migrations, so its schema can be older than the code; and nothing proves it holds no data. After this change it arises only from a process crash between the initialisation commit and the row insert, from a release before 42.3, or from an older pod during a rolling deploy.

### W4. Startup migrations skip empty workspaces and explain a missing database (`internal/migrations/manager.go`)

- "A workspace migration is pending" means some migration in `migrationsToRun` has `HasWorkspaceUpdate()`; a system-only migration never connects to a workspace (`:242`). The ahead-of-code refusal (`:158-161`) and the equal-versions early return stay as they are.
- In each workspace migration loop, after connecting, a workspace whose database holds no tables (`WorkspaceDatabaseHoldsTables`), or whose connection fails with 3D000 (the connector keeps the `pq` error wrapped), is looked at again **inside the name lock**, through a lock field on the manager (default `database.WithWorkspaceDatabaseLock`). The lock waits for an initialisation in progress on another instance (a connection manager recreating a missing database commits its whole schema at once, so it looks empty until then) and for a `Delete` in progress (W5). Inside it, on the migration's system transaction:
  - row gone → skipped;
  - database missing, row present → the migration fails with `workspace <id> is registered but its database <name> does not exist: if DB_PREFIX changed, restore it; otherwise create an empty database named <name> owned by <database user> (startup skips empty databases) or delete the workspace's rows`. The database is never created here (D2). The message names the empty-database way out because the console is unreachable while startup fails, and the owner because an empty database owned by another role leaves Notifuse unable to create tables in `public` (PostgreSQL 15 and later);
  - database empty → skipped and logged. There is nothing to migrate, and it keeps no schema a migration could act on: part B's repair will give it the current schema, so pending migrations never run on a freshly built schema (D3). Until part B, such a workspace stays broken on requests, as today, but no longer stops startup;
  - database now holds tables (an initialisation committed while the migration waited) → migrated as any other, after the lock is released.
- `workspaceConnector.connectToWorkspace(ctx, cfg, workspaceID)` gains a context and pings with `PingContext`; its DSN comes from a new `workspaceMigrationDSN(cfg, workspaceID)` that adds `connect_timeout=10` (the context alone does not bound TLS and startup in lib/pq v1.10.9), testable on its own. All three test implementations change with it.

Known gaps, not fixed here: a workspace already registered with a **partial** schema (from a failed creation on an earlier version) holds tables, so it is migrated as today; a future workspace migration touching a missing table still stops startup, with the error naming the workspace, and recovery stays manual. The name lock is taken while `executeMigration`'s system transaction is open: a future system migration that locks `workspaces` rows could deadlock with a concurrent `Delete`. PostgreSQL does not detect it (each side waits in Go for another connection of its own process, so the server sees no cycle); it ends when `Delete`'s 10-minute bound expires and rolls its lock back. No migration does that today; a comment in `executeMigration` says so.

### W5. Delete under the name lock (D8) (`internal/repository/workspace_postgres.go`)

- `Delete` runs its pool close, its drop and its row deletion inside `WithWorkspaceDatabaseLock` (the same detached, bounded context as today), using an unlocked drop internally. That drop stays on `r.systemDB` with today's pre-13 fallback; `fn`'s `admin` handle is not used by `Delete`. The repository reaches the lock through a field (`workspaceDatabaseLock`, defaulting to `database.WithWorkspaceDatabaseLock`), so its sqlmock tests run `fn` through a pass-through fake instead of dialling a real admin database.
- With W2's in-lock `stillRegistered`, a request arriving during a `Delete` (problem 8) waits on the lock, finds the workspace gone and creates nothing, so delete-then-create of the same name keeps working.
- `DeleteDatabase` leaves `domain.WorkspaceRepository` and the repository (mock regenerated): after this change nothing calls it. Its tests move to `Delete`.
- Unchanged: the drop still goes first and a failed drop aborts with nothing changed; a failed row deletion after a successful drop still leaves a registered workspace without a database, which the fallback recreates on the next request, as today.

## Decisions (Pierre, 2026-10-31)

- **D2.** A missing database is never created at startup; the migration fails with the actionable message. Creating it would turn a changed `DB_PREFIX` into one silently empty database per workspace.
- **D3.** A workspace with an empty database never receives pending migrations: migrations skip it, and part B's repair builds the current schema. Fresh workspaces are never migrated today; running migrations on a fresh schema would rely on every past migration being idempotent on it, which nothing tests (the parity test covers only the web analytics and annotations tables).
- **D4.** A leftover database holding tables at creation is refused with 409, never dropped automatically.
- **D5.** Failure injection through injected dependencies (open, initialise, lock, row check, insert), no exported test hook. `WithWorkspaceDatabaseLock` is exported for its production callers, not for tests, though the integration barrier uses it.
- **D8.** The delete race (problem 8) is closed with the name lock.
- **Split** (2026-10-31): D1, D6 and D7 are in part B. D8 was first put there too, and moved back after a review showed part A alone would make problem 8 a permanent 409.
- **Release and delivery** (2026-10-31): 42.2 ships first with the batch already staged; parts A and B ship together in 42.3, as two commits of one PR.
- **Lock keepalives** (2026-10-31): chosen by Pierre for part B's migration lock, whose wait is unbounded; applied by the shared lock-transaction helper, so the name lock gets them too.
